Firewall Rules and Access Control

Creating four VLANs took maybe twenty minutes in the Omada interface once I knew what I wanted. Deciding exactly what should be allowed to pass between them took a lot longer, and it taught me more about networking than the VLAN setup itself ever did.

Finding where the rules actually live

My first instinct was to look for a settings page literally called "Firewall," and Omada does have one, but it turned out to mostly contain connection timeout settings and not much else useful for what I wanted. The actual inter-network policy lives in a separate section called Gateway ACL, short for access control list. That's a small but genuinely useful lesson on its own. On a lot of router platforms, the feature that actually controls what one network is allowed to do to another isn't necessarily labeled "firewall" at all, and it's worth poking around the whole interface before assuming a feature doesn't exist just because it isn't where you expected it.

The rule set

The final policy comes down to a short, ordered list of rules. Order matters a lot in ACL systems like this one, since the first matching rule wins and everything after it is skipped for that particular piece of traffic.

RuleDirectionResult
Allow_LAN_to_WANAny VLAN to internetPermit
Allow_VLAN1_to_All_InternalVLAN 1 to VLAN 10, 20, 30Permit
Allow_VLAN10_to_All_InternalVLAN 10 to VLAN 1, 20, 30Permit
Deny_Guest_to_InternalVLAN 20 to VLAN 1, 10, 30Deny
Deny_IoT_to_TrustedVLAN 30 to VLAN 1, 10Deny

Reading that top to bottom, everyone gets internet access through the first rule, the two trusted networks can reach everything else, and Guest and IoT get explicitly blocked from reaching back into the trusted side. Guest and IoT devices still get internet through that first rule, they just can't reach anything internal beyond it.

A real problem: the IoT exception for Plex

That deny rule for IoT created an actual, practical problem almost immediately after I turned it on. A Google TV living on the IoT network needed to reach a Plex server sitting over on the trusted network, and the deny-everything policy blocked that connection outright, which meant the TV couldn't see the Plex library at all anymore. The tempting fix would have been to just move the Google TV onto the trusted network, or delete the deny rule entirely and call it a day. I didn't want to do either, since that throws away the whole point of isolating IoT devices from the trusted side in the first place.

Instead I added one more rule, placed above the broad IoT deny rule so it gets evaluated first and wins before the deny rule ever gets a chance to apply:

Allow_IoT_to_Plex
    Direction: LAN to LAN
    Source: IoT (VLAN 30)
    Destination: Plex server's reserved address
    Protocol: TCP
    Port: 32400
    Policy: Permit

That one narrow exception, IoT devices can reach exactly one address on exactly one port, is a small but real example of least-privilege thinking in practice. The Google TV doesn't need to see my laptop or reach any file shares on my network, it needs to talk to Plex on port 32400 and nothing else at all. Giving it exactly that and nothing more is a lot more defensible than "IoT can reach the trusted network now" as a blanket policy change, and it kept the rest of the isolation intact while fixing the one thing that actually broke.

What this taught me about network security

The thing that stuck with me most from this whole exercise is that segmentation and access control are really two separate design problems that happen to live in the same interface. Segmentation, putting devices into different VLANs, is mechanical and quick, and you can do it in an afternoon without thinking too hard. Deciding what's allowed to cross between those segments is where the actual security thinking happens, and it never resolves into one clean rule that handles everything. It's always a list of specific, narrow exceptions layered on top of a default-deny posture, which is exactly what real firewall configurations tend to look like once you get past the tutorial stage and start dealing with devices that actually need to talk to each other for a good reason.

ACL evaluation order (first match wins)

    1. Allow_LAN_to_WAN              -> everyone gets internet
    2. Allow_VLAN1_to_All_Internal   -> wired trusted, full access
    3. Allow_VLAN10_to_All_Internal  -> main WiFi, full access
    4. Allow_IoT_to_Plex             -> narrow exception, TCP 32400 only
    5. Deny_Guest_to_Internal        -> guest blocked from internal
    6. Deny_IoT_to_Trusted           -> IoT blocked from internal (except above)
