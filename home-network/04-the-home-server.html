The Home Server

For the self-hosted side of this project, Pi-hole for ad blocking, and eventually a place to stream games and watch the occasional movie on the living room TV, I needed one small machine that could sit somewhere in the apartment and run quietly in the background. Picking that machine turned into its own small research project.

Why not a Raspberry Pi

My first instinct was a Raspberry Pi 5, since that's what most homelab guides default to and it has a well earned reputation for this kind of thing. But when I actually listed out what I wanted the machine to do, none of it needed to run at the same time. I wasn't going to be streaming a game, watching a movie, and running an emulator at the same moment. Pi-hole and any other background service would just sit there sipping a small amount of memory and CPU most of the day. That changes the math on hardware quite a bit.

Once I priced things out, an 8GB Raspberry Pi 5 setup and a small mini PC ended up costing about the same, somewhere around a hundred fifty to a hundred seventy dollars either way, once you account for a case, power supply, and storage for the Pi. I went with a mini PC instead, a Beelink MINIS 12 Pro with an Intel N100 processor, 16GB of RAM, and a 500GB SSD. That gave me a real x86 machine running full Ubuntu without any of the ARM compatibility quirks you sometimes run into on a Pi, noticeably more RAM for running several background services at once, and an actual SSD instead of relying on a microSD card for anything beyond casual use. For a device I planned to leave running constantly and eventually depend on for DNS across my whole network, that felt like the safer bet.

Picking the OS and the two modes it runs in

I installed Ubuntu Server rather than the desktop edition, since the machine was going to spend most of its life with nobody looking at a screen attached to it. The hostname ended up being ANKIT-MINI-S, which shows up throughout the setup and configuration for everything that came after it.

The machine needed to do two very different jobs depending on the moment. Most of the time it should sit quietly running background services nobody has to think about. Occasionally I wanted to actually sit down and use it, streaming a game from my main PC or watching something through Plex on the living room TV. I solved that by keeping the machine in a lightweight, no-desktop mode by default, using systemd's multi-user target instead of the full graphical target, and only starting the graphical desktop on the occasions I actually wanted to sit at the machine. That way the background services don't have to fight a full desktop environment for resources they don't need most of the day, and the machine draws less power sitting idle overnight. Switching between the two modes ended up being just a couple of systemctl commands, one to set the default boot target and another to start the graphical session on demand.

Two modes on one machine

      ANKIT-MINI-S (Beelink MINIS 12 Pro, Ubuntu Server)

      Default: server mode (multi-user.target, no desktop)
         - background services run here all the time

      On demand: entertainment mode (graphical.target)
         - started manually when I want to sit at the machine
         - game streaming, Plex client, light emulation

Managing it remotely, and a loopback surprise

Day to day I manage this machine over SSH, since it's fast and scriptable and doesn't require anything extra running on the server itself. I also set up Cockpit, a web based Linux admin panel, for the times I want a quick visual look at CPU load, memory, running services, or disk usage without typing out a string of commands. The two tools aren't really competing. SSH is for doing things and troubleshooting, Cockpit is for glancing at the machine's health from my phone or another computer without opening a terminal.

Getting Cockpit working the first time hit one small snag that's a classic Linux gotcha. The machine reported its own address as 127.0.1.1, its loopback address, instead of its real address on the local network. That address only means anything to the machine itself. No other device on the network can reach a machine by its loopback address, so pointing a browser at it from another computer just failed silently. Once I looked up the machine's actual address on the local network and pointed my browser there instead, Cockpit came up immediately. I also enabled Cockpit's socket service so it starts automatically on boot, rather than needing to be launched by hand every time the machine restarts.
