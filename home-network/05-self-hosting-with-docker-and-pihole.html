Self-Hosting with Docker and Pi-hole

With the mini PC set up and running, the next question was how to actually run the services I wanted on it. I settled on Docker for everything, and the first real service to go on the machine was Pi-hole, which turned out to produce some of the better troubleshooting stories from this whole project.

Why Docker instead of installing things directly

Every self-hosted service on this machine runs inside a Docker container rather than being installed straight onto the OS. That decision paid off almost immediately once I started actually using it. Docker containers restart automatically if they crash, so a service doesn't just quietly stay down until I notice. They keep their configuration in mounted folders that survive a container being deleted and rebuilt from scratch, which meant I could break something badly while experimenting and not lose my actual settings. They also don't leave stray files and half-removed dependencies scattered across the base OS if I decide to rip a service out later, which matters a lot on a machine I plan to keep running for years. Just as important, everything keeps running whether or not the graphical desktop is active, which fits the whole point of having a machine that mostly runs headless in the background.

Pi-hole's DNS wasn't answering, even though its dashboard was fine

Getting Pi-hole running in Docker looked successful at first. The admin dashboard loaded without any trouble, and gravity updated and pulled in over a hundred thousand blocklist domains with no errors. But when I pointed a device at it for DNS, nothing came back. No blocked ads, no resolved domains, nothing.

My first instinct was to assume something was wrong with Pi-hole's upstream DNS server, the resolver it forwards requests to when a domain isn't on any blocklist. I tested that directly from the Linux machine itself with a plain nslookup against Cloudflare's public resolver, and it worked immediately. That ruled out anything related to internet connectivity or the upstream resolver Pi-hole depends on. The real answer was sitting in Pi-hole's own container logs the whole time: failed to create listening socket for port 53: Address in use. Something else on the Linux host, in this case Ubuntu's own systemd-resolved service, was already sitting on port 53, so Pi-hole's DNS server couldn't bind to that port at all, even though every other part of Pi-hole, the web dashboard included, was running completely normally.

Disabling the stub listener that systemd-resolved uses freed up port 53, and DNS queries against Pi-hole started returning real answers right away. The lesson that stuck with me here is that a service's web dashboard loading fine tells you almost nothing about whether its actual core function is working underneath. Pi-hole's UI has no idea whether its DNS listener is bound to anything at all, it just renders the interface regardless.

The password that was set but somehow wasn't

A smaller but genuinely confusing issue came up right after. I set a Pi-hole web password directly in the Docker Compose environment variables, and confirmed with docker inspect that the variable really was present inside the running container, spelled correctly, with the value I expected. Pi-hole still generated and displayed its own random temporary password on startup instead, and the password I'd set didn't work at all when I tried logging in with it.

That turned out to be a useful reminder that an environment variable existing inside a container doesn't guarantee the application actually reads it as the current, active setting, especially once persistent configuration is already stored on disk from a previous run of the same container. Pi-hole had already written its own password to a config file the first time it ever started, and it was reading from that file instead of re-checking the environment variable on every restart. The fix ended up being Pi-hole's own built-in command for exactly this situation, pihole setpassword, run directly inside the container, which set the password properly regardless of what the environment variable said or what was already on disk.

Same symptom, two different root causes

      Symptom: Pi-hole isn't behaving the way I configured it

      Case 1: DNS queries get no answer
        -> dashboard fine, but container log shows port 53 already in use
        -> fix: disable systemd-resolved's stub listener

      Case 2: my password doesn't work
        -> docker inspect shows the right env var, but Pi-hole ignores it
        -> fix: run `pihole setpassword` inside the container directly

What both of these had in common

Neither of these problems showed up anywhere near the surface. Pi-hole's dashboard, its setup wizard, and its general responsiveness all looked completely normal in both cases. The actual answer in both was buried in a log file or required checking a layer underneath the application itself, the host OS in one case and Pi-hole's own persisted config in the other. That became a pattern I leaned on for the rest of this project. When something looks like it should work and doesn't, check the layer just underneath the one that's complaining before assuming the obvious explanation is the right one.
